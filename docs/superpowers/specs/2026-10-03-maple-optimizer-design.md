# Maple Optimizer — 설계 문서

- 작성일: 2026-10-03
- 상태: 설계 확정, 2026-10-03 실측 반영(전투력 미계산, 프리셋 기반 보스 세팅, 1단계를 1a·1b로 분할)

## 1. 목적

메이플스토리(KMS) 캐릭터 닉네임을 넣으면 현재 스펙을 불러와, 다음 질문에 **수치로** 답하는 공개 웹 서비스.

1. 이 템으로 바꾸면 보스 실딜(스탯공격력·환산)이 얼마나 오르나
2. 경매장 매물이 억당 얼마나 효율적이고, 직작 기댓값 대비 싼가 비싼가
3. 스타포스·큐브·추옵을 직접 하면 비용 분포가 어떤가
4. 예산 X억으로 무엇을 어떤 순서로 하면 가장 많이 오르나
5. (관리자 전용) 위 질문을 채팅으로 묻는 AI 에이전트

서버 구축·배포 경험 자체도 목표에 포함된다.

## 2. 확정된 결정과 근거

| 결정 | 내용 | 근거 |
|---|---|---|
| 대상 | 전 직업 범용 (닉네임 입력) | 사용자 선택 |
| 형태 | 공개 웹 서비스 | 서버까지 해보고 싶다는 목표 |
| 스택 | FastAPI + React(Vite), Docker Compose, Oracle Always Free ARM VM | 기존 my-agent에서 쓴 스택. 엔진을 프레임워크와 분리해 검증 |
| 경매장 데이터 | 사용자 수동 입력 (폼, 채팅 붙여넣기) | 넥슨 Open API에 메이플 경매장 엔드포인트 없음(마비노기만 있음). 패킷 캡처·메모리 읽기는 약관 위반이라 하지 않음 |
| 환산 사이트 | MapleScouter 데이터는 가져다 쓰지 않음. 사람이 수동 비교하는 검증 기준으로만 사용 | 공개 API 없음, 스크래핑은 약관·안정성 문제 |
| 평가 지표 | 보스 실딜 지수(스탯공격력 × 보공 × 크뎀 × 방무)와 환산 주스탯. **전투력은 계산하지 않고** API 값을 참고로만 표시 | 실측(2026-10-02/03): 스탯공격력 공식은 API 46명·인게임 2화면에서 반올림 오차(0.001%) 이내로 일치. 전투력은 같은 순간의 스탯으로 재현되지 않고(회귀 최대 2배 오차) 스탯이 바뀌어도 갱신되지 않는 경우가 있음. 커뮤니티 전투력 공식에는 방무도 없음 |
| 기준 세팅 | 장비·하이퍼스탯·어빌리티 프리셋 조합(3×3×3=27개)을 엔진으로 모두 평가해 보스 실딜 최대 조합을 기본 "보스 세팅"으로 쓰고, 사용자가 바꿀 수 있다 | API 스냅샷은 그 순간의 프리셋·버프 상태 그대로다(사용자 캐릭터가 사냥 프리셋 상태로 기록됨). 보스용 하이퍼 프리셋이 둘(2, 3)이라 옵션 개수 휴리스틱으로는 못 가름 |
| 에이전트 | Claude tool use, 관리자 전용 | LLM 비용 통제. 나중에 사용량 제한을 붙여 공개 가능 |
| 숫자 원칙 | LLM은 숫자를 만들지 않는다. 모든 수치는 엔진 도구 결과에서만 | 그럴듯한 틀린 수치 방지 |

## 3. 전체 구조

```
maple-optimizer/
├── engine/        순수 Python. 웹·API·LLM 의존성 없음
│   ├── data/        정적 테이블 (JSON, 출처·패치일 표기)
│   ├── stats/       직업 프로필, 스탯 합산, 잔차 보정, 데미지 모델, Metrics
│   ├── enhance/     스타포스·큐브·추옵 비용 분포
│   ├── market/      매물 평가, 직작 기댓값 대비
│   └── optimize/    예산 최적화
├── nexon/         넥슨 Open API 클라이언트 + JSON → 엔진 도메인 모델 변환
├── server/        FastAPI: 공개 계산 API, 캐시, 호출 제한, 관리자 인증, 에이전트 엔드포인트
├── agent/         Claude tool use 루프, 도구 래퍼, 시스템 프롬프트
├── web/           React + Vite
└── deploy/        Docker Compose, Caddyfile, GitHub Actions 워크플로
```

의존 방향: `web → server → (agent, nexon) → engine`. `engine`은 다른 패키지를 import하지 않는다. 넥슨 JSON 형태는 `nexon/` 안에서만 다룬다.

## 4. 빌드 순서

각 단계는 독립적으로 동작하고 검증 가능한 결과물을 낸다.

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 1a | `nexon` 클라이언트, 옵션 문자열 파서, 직업·무기 상수 테이블, 스탯공격력 공식, 스냅샷 파싱 | 표본 46명(데몬어벤져 제외) fixture 전원에서 엔진 `최대 스탯공격력` = API 값(상대 오차 0.01% 이내) |
| 1b | 잔차 분해, 아이템 교체, 세트 효과, 프리셋 조합 평가, 보스 실딜 지수 | 같은 캐릭터의 사냥 세팅 스냅샷에서 보스 세팅 전환을 예측한 스탯공격력이 실제 보스 세팅 스냅샷 값과 1% 이내(두 시점의 버프 차이는 오차 요인으로 보고) |
| 2 | `engine/market` + `server` + `web` 기본 화면 + 첫 배포 | 공개 URL에서 닉네임 조회 → 매물 입력 → 억당 효율 표 |
| 3 | `engine/enhance` + 매물의 직작 기댓값 대비 + 내 운 분석 | 스타포스 정확 계산 평균과 몬테카를로(10만 회) 평균의 차이 1% 이내, 큐브 목표 확률 테스트 |
| 4 | `engine/optimize` | 소규모 후보에서 탐욕법 결과와 전수 탐색 최적값의 차이 측정·보고 |
| 5 | `agent` | 고정 시나리오 평가 통과 (도구 선택, 숫자 출처 검사) |

## 5. 계산 엔진

### 5.1 스탯공격력 공식 (검증됨)

```
최대 스탯공격력 = 스탯 × 공(마) × (1 + 데미지%) × (1 + 최종 데미지%) × 무기 상수
  스탯 = (주스탯 × 4 + 부스탯 합) / 100
  공(마) = API `공격력`/`마력` (이미 % 적용된 최종값)
```

- 무기 상수(실측): 1.2 스태프·완드·카르타·샤이닝 로드·ESP 리미터·매직 건틀렛·한손둔기, 1.3 활·듀얼 보우건·에인션트 보우·브레스 슈터·단검·장검·차크람·체인·부채·케인·튜너, 1.3125 에너지소드, 1.34 두손검, 1.35 석궁, 1.44 두손도끼, 1.49 창·폴암·태도, 1.5 건·핸드캐논, 1.7 너클·소울슈터, 1.75 아대. 표에 없는 무기는 "계산 제외"로 명시한다.
- 직업: 제논은 (STR+DEX+LUK)×4/100, 부스탯 없음. 렌은 STR/DEX. 섀도어·듀얼블레이더·카데나는 부스탯 DEX+STR. 데몬어벤져는 API HP가 표시 상한(500,000)이라 1차 범위 밖.
- 전투력: 계산하지 않는다. API 값을 "참고(인게임 기록값)"로 표시한다.

### 5.2 보스 실딜 지수

```
실딜 지수 = 최대 스탯공격력 × (1 + 데미지% + 보공%)/(1 + 데미지%) × (1.35 + 크뎀%) × (1 − 보스 방어율 × (1 − 방무))
방무 합산 = 1 − Π(1 − xᵢ)
  추가: 1 − (1 − 기존)(1 − x)
  제거: 1 − (1 − 기존)/(1 − x)
```

보스는 `BossProfile`(이름, 방어율)로 고른다. 기본 프리셋 몇 개를 데이터 테이블로 둔다.

### 5.3 환산 주스탯

변경 전후 실딜 지수 비율을 같은 비율을 내는 주스탯 증가량으로 역산해 표시한다. 정의를 문서와 화면 도움말에 명시한다(사이트마다 정의가 다르기 때문).

### 5.4 기준값 + 차이 방식

최종 스탯을 처음부터 재현하지 않는다.

1. `character/stat`의 최종 스탯을 기준값으로 받는다.
2. 주스탯은 `⌊(기본 + 고정) × (1 + %)⌋ + %미적용 고정` 구조로 분해한다. 장비(`item-equipment`), 세트 효과, 하이퍼스탯, 어빌리티, 유니온, 심볼 등 API로 보이는 출처를 합산하고, 보이지 않는 나머지는 **잔차**로 두어 모델 값이 API 최종값과 정확히 같아지게 역산한다.
3. 교체 시 기존 템 기여분을 빼고 새 템 기여분을 더해 재계산한다. 잔차는 고정한다.
4. 세트 효과는 교체 후 착용 목록으로 다시 계산한다. 럭키 아이템 등 예외는 1차 범위 밖이며, 해당 시 "계산 제외"를 명시한다.
5. 프리셋 전환(장비·하이퍼·어빌리티)도 교체의 한 종류로 처리한다. 27개 조합을 모두 평가해 실딜 최대 조합을 기본 보스 세팅으로 제안한다.
6. 버프: 스냅샷에 그 순간의 버프가 섞여 있고 잔차가 흡수한다. 같은 프리셋 조합이 적용된 최근 날짜들 중 스탯공격력이 가장 낮은 날을 기본 기준 스냅샷으로 쓰고, 사용자가 날짜를 고를 수 있다. 기준 날짜를 화면에 표시한다.

### 5.5 도메인 타입 (dataclass)

- `JobProfile`: 주스탯, 부스탯 목록, 공/마 구분, 예외 규칙
- `StatBlock`: 스탯별 고정, %, %미적용 고정, 공/마, 공/마%, 데미지%, 보공%, 크뎀%, 최종뎀%, 방무 리스트
- `Item`: 슬롯, 이름, 레벨, 세트, 출처별 StatBlock(기본, 스타포스, 추옵, 잠재, 에디, 주문서)
- `CharacterSnapshot`: 직업, 레벨, 날짜, API 최종 스탯, 장비 목록, 잔차
- `Metrics`: 스탯공격력, 실딜 지수, 환산 주스탯 (+ 참고용 API 전투력)
- `evaluate(snapshot, changes: list[ItemSwap], boss: BossProfile) -> Evaluation(before, after, delta)`

### 5.6 정적 데이터 테이블 (`engine/data/`)

직업 프로필, 세트 효과, 아이템 기본 스탯, 스타포스 단계별 증가량(아이템 레벨별), 추옵 단계 수치, 잠재·에디 옵션 수치, 스타포스 확률, 큐브 등급업·옵션 확률(넥슨 공개 확률표), 보스 프리셋. 파일마다 출처 URL과 기준 패치일을 기록한다. 패치가 오면 테이블만 교체한다.

## 6. 강화 (`engine/enhance`)

- 결과는 분포: 평균, 중앙값, p75, p90.
- 스타포스: 단계별 성공/실패/파괴 마르코프 체인. 정확 계산과 몬테카를로를 교차 검증한다. 입력: 파괴 시 복구 비용(스페어 시세), 스타캐치, 파괴 방지, 이벤트(할인, 특정 단계 100% 등).
- 큐브(잠재·에디): 목표 조건(예: 보공 2줄 이상, 주스탯 % 합 ≥ 33)의 1회 성공 확률 p를 줄별 확률 조합으로 계산하고, 소모 개수는 기하분포. 등급업 비용을 더한다.
- 추옵: 목표(예: 환산 140급 이상)의 성공 확률을 옵션 종류·단계 분포로 계산한다.
- 내 운 분석: `확률 정보 조회` API의 사용 기록으로 실제 지출을 구하고, 같은 목표의 비용 분포에서 백분위를 보여준다.

## 7. 매물 평가 (`engine/market`)

- 입력: 아이템명(자동완성 → 기본 스탯 자동), 스타포스, 잠재 3줄, 에디 3줄, 추옵 수치, 가격, (선택) 기존 템 판매 예상가.
- 출력: 교체 시 Metrics 변화(세트 포함), 억당 효율 = 실딜 상승률 ÷ (가격 − 기존 템 판매가), 직작 기댓값 대비(베이스 템 가격 + 스타포스 + 큐브 + 추옵 비용 분포에서 매물 가격의 위치).
- 표시 예: "매물 45억 / 직작 기댓값 62억 (중앙값 51억, p75 78억) → 기댓값의 73%. 직작하면 68% 확률로 45억보다 더 듦".
- 여러 매물을 효율순 표로 보여준다. 매물 목록은 브라우저 localStorage에 저장한다.

## 8. 예산 최적화 (`engine/optimize`)

- 후보 행동: 매물 구매, 스타포스 +n, 큐브 목표, 추옵 목표. 각 행동은 비용(사용자가 고른 위험 기준: 평균 또는 p75, 기본 p75)과 상승량을 가진다.
- 제약: 부위당 하나(매물 구매 시 그 부위의 기존 템 직작 후보 제거), 세트 효과, 곱연산 상호작용.
- 알고리즘: 재평가 탐욕법 — 억당 효율 최고 행동을 적용하고, 적용된 상태에서 나머지 후보를 다시 평가하기를 예산이 남는 동안 반복.
- 출력: 순서가 있는 추천 목록, 누적 비용, 누적 상승률.

## 9. 서버 (`server/`)

- 공개 엔드포인트: 캐릭터 조회, 교체 평가, 매물 평가, 강화 비용, 예산 최적화.
- 넥슨 API 키는 서버 `.env`에만 둔다. 프론트는 넥슨을 직접 호출하지 않는다.
- 캐시(SQLite): 키 `(ocid, endpoint, date)`. 과거 날짜는 영구, 당일은 짧은 TTL(기본 15분, 넥슨 반영 주기 확인 후 조정). 닉네임→ocid도 캐시.
- 호출 제한: IP별 요청 제한 + 넥슨 키 한도(개발/서비스 단계)에 맞춘 전역 큐. 정확한 한도는 구현 계획 단계에서 확인한다. 공개 전 서비스 단계 키를 신청한다.
- 관리자 인증: `.env`의 비밀번호 해시 + 서명된 세션 쿠키. 에이전트 엔드포인트만 보호한다.

## 10. 에이전트 (`agent/`)

- Claude API tool use 루프. 모델·SDK 세부는 구현 계획 단계에서 최신 문서로 확정한다.
- 도구: `lookup_character`, `evaluate_swap`, `evaluate_listing`, `enhance_cost`, `optimize_budget` — 엔진 함수의 얇은 래퍼.
- 채팅에 붙여넣은 매물 텍스트는 에이전트가 구조화하고, 해석 결과를 먼저 보여준 뒤 계산한다.
- 시스템 프롬프트: 모든 수치는 도구 결과에서만 인용한다. UI는 답변마다 근거 도구 호출 결과를 펼쳐볼 수 있게 한다.
- SSE 스트리밍, 대화는 SQLite 저장, 일일 토큰 예산 상한(`.env`) 초과 시 중단.

## 11. 배포 (`deploy/`)

- Docker Compose: `api`(FastAPI), `caddy`(리버스 프록시, 자동 HTTPS, React 빌드 정적 서빙).
- 대상: Oracle Always Free ARM VM → arm64 이미지.
- CI/CD: GitHub Actions에서 이미지 빌드 → VM에 SSH로 `docker compose pull && docker compose up -d`.
- README에 시크릿 소재지를 기록한다: VM `.env`(넥슨 키, Claude 키, 관리자 비밀번호 해시, 세션 서명 키), GitHub Actions Secrets(SSH 키, 레지스트리 토큰). 저장소에는 `.env.example`만 둔다.

## 12. 에러 처리

- 실패는 반드시 사용자에게 보인다. SSE 스트림 중 예외도 오류 이벤트로 보내고 프론트가 표시한다.
- 넥슨 오류를 구분해 안내한다: 캐릭터 없음 / 키 한도 초과 / 점검 중. 가능하면 캐시로 대체하고 "어제 데이터로 계산"처럼 명시한다.
- 엔진이 처리 못 하는 항목(미지원 직업 예외, 테이블에 없는 아이템)은 추정하지 않고 "계산 제외"로 명시한다.

## 13. 테스트

- `engine`: 실제 API 응답을 녹화한 fixture로 엔진 스탯공격력 = API 값, 사냥↔보스 세팅 스냅샷 쌍으로 프리셋 전환 예측 검증, 스타포스 정확 계산 ↔ 몬테카를로, 탐욕법 ↔ 전수 탐색.
- `nexon`: 녹화 응답 기반 테스트, 실호출은 수동 스모크 테스트만.
- `server`: FastAPI TestClient, 넥슨 클라이언트 mock.
- `agent`: 고정 시나리오 평가 — 올바른 도구 호출 여부, 답변의 모든 숫자가 도구 결과에 존재하는지 자동 검사.
